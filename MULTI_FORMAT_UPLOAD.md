# Arik: Multi-Format Document Upload

Extends GUIDED_DOCUMENT_SCANNING.md, which covers the live camera-capture
flow specifically. This doc covers the other real intake path: a patient
already has a file - a PDF downloaded from an email or insurer portal, or
a screenshot taken on their phone or computer - and just needs to upload
it directly, no camera guide needed since the file is already captured.

## Three real intake sources, not one

1. **Guided camera capture** (GUIDED_DOCUMENT_SCANNING.md) - live camera
   view, on-screen alignment guide, quality checks before accepting
2. **Plain file upload** - a standard file picker, for a PDF already
   downloaded or a screenshot already taken. No camera guide applies here
   since there's no live framing/blur/glare problem to solve - the file
   already exists in whatever quality it was captured at
3. **Screenshots specifically** - functionally the same as any other
   image upload (PNG/JPEG), but worth naming explicitly since it's a very
   common real path: a patient screenshots a portal page or an email
   attachment preview rather than downloading the original file

## PDF handling: try text extraction before treating it as an image

PDFs come in two real varieties, and they need different handling:

- **Native/text PDFs** - most PDFs generated by an insurer portal, a
  billing system, or an emailed statement have actual embedded text, not
  just a picture of a page. **Extract this text directly** using a PDF
  parsing step (e.g. `pdf-parse` or similar in Node) before ever
  considering the vision model. This is faster, cheaper (text tokens
  only, no image tokens), and more accurate than routing through OCR/
  vision extraction, since there's no risk of a model misreading a
  character.
- **Scanned/image-only PDFs** - some PDFs are just a scanned image of a
  paper document with no embedded text layer at all (common for older
  hospital billing systems or a fax-to-PDF conversion). For these, fall
  back to rasterizing each page to an image and sending those to the
  extraction-tier model exactly as if they were camera-captured photos.

**Detection logic**: attempt text extraction first; if the extracted
text is empty or below a reasonable length threshold (suggesting an
image-only PDF), fall back to the rasterize-and-vision-model path
automatically, without asking the patient to know or care which kind of
PDF they have.

## Image format handling

- Standard PNG/JPEG uploads (including screenshots) go straight to the
  extraction-tier model as image input - same path already established
  for camera captures
- **HEIC** (the default format for iPhone photos and some iPhone
  screenshots) needs a conversion step before reaching the model, since
  most vision APIs don't accept HEIC directly - convert to JPEG either
  client-side (browser-based conversion libraries exist) or server-side
  on upload, transparently, before extraction runs

## What this means for the build

- `uploaded_documents` schema already supports this - add a
  `source_format` field (`'camera_capture'`, `'pdf_native'`,
  `'pdf_scanned'`, `'image_upload'`) alongside the existing `doc_type`
  (which describes content - bill, EOB, denial letter - a separate axis
  from how the file arrived)
- Upload UI needs both paths available from the same entry point: "Take
  a photo" (opens GUIDED_DOCUMENT_SCANNING.md's camera flow) and "Choose
  a file" (standard file picker accepting PDF/PNG/JPEG/HEIC) - not one or
  the other
- The PDF text-extraction path is genuinely cheaper to run than every
  other intake method here, worth noting in cost tracking since a
  patient who downloads a clean PDF from their insurer portal costs
  meaningfully less to process than one who photographs a paper bill
- No change to the extraction-tier model choice (Haiku 4.5, per
  HANDOFF.md's locked routing) - this is entirely a preprocessing layer
  before that model call, not a change to which model gets called
